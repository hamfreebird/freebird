# AGENTS.md

Freebird is a single-crate Rust implementation of a stack-based language. `readme.md` is the intended spec, `USAGE.md` covers the CLI, and `IMPROVEMENTS.md` is a dated v3 audit of known gaps. Docs and code comments are Chinese; `readme.md` and `USAGE.md` describe features that are not fully implemented — trust `src/` and the tests when they conflict.

## Commands

- Build: `cargo build --release` (edition 2024, Rust 1.85+).
- Test: `cargo test` — current baseline is 232 unit + 196 integration tests, all green (`tests/integration_test.rs` 33 + `tests/m0_test.rs` 28 + `tests/m1_test.rs` 21 + `tests/m2_test.rs` 58 + `tests/m3_test.rs` 35 + `tests/m4_test.rs` 13 + `tests/m5_test.rs` 5 + `tests/snapshot_test.rs` 1 + `tests/differential_test.rs` 2).
- Single test: `cargo test <test_name>`; integration only: `cargo test --test integration_test test_fib_program`, `cargo test --test m0_test`, `cargo test --test m1_test`, `cargo test --test m2_test`, `cargo test --test m3_test`, `cargo test --test m4_test`, `cargo test --test differential_test`.
- CLI: `run`/`check`/`build` accept `<file.fb>` or `--manifest-path <freebird.toml|dir>` (auto-detects `./freebird.toml` when no file is given); `build` also supports `--target stardust|llvm`, `-o`, `--emit ir|exe`, `--opt-level`, `--stardust-bin`, `--no-opt`, `--link-stardust <path>`. Other commands: `fmt`, `lsp`, `dap`, `repl`.
- Run tests from the repo root: integration tests load fixtures via relative paths. `tests/programs/*.fb` and `examples/*.fb` are discovered automatically by `tests/differential_test.rs`; add a same-named `.in` file for stdin. Add explicit tests for new behavior, and keep fixtures runnable on both backends.

## Toolchain gotchas

- CI (`.github/workflows/ci.yml`) runs `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, a release build, `cargo test`, `check-doc-links.py`, `check-fixtures.py`, `check-docs.py`, and an examples smoke test. The `llvm` job runs `tests/m3_test.rs` with clang; the `bench` job is advisory. `.github/workflows/release.yml` checks the tag against `Cargo.toml` and packages `freebird-linux-x86_64` (+ sha256) for `v*` tags.
- Pipeline tests now assert output values for fib/while/struct/enum/`stardust!`; only the two `check_source` positive cases remain `is_ok()`. The Stardust integration tests compare interpreter output against `run_source` byte-for-byte. `tests/m0_test.rs` holds the M0 negative diagnostics and VM/Stardust differential cases; add output or VM-state assertions when changing behavior.
- `tests/snapshot_test.rs` pins diagnostics as `code level line` in `tests/snapshots/diagnostics.txt`; update with `UPDATE_SNAPSHOTS=1 cargo test --test snapshot_test`. `scripts/check-fixtures.py` validates fixture naming/stdin pairs.
- `RuntimeConfig::test()` is the convention for program tests (max_stack 1024, max_call_depth 64, max_steps 1M, debug=true); CLI defaults are much larger. `run --debug` now selects `RuntimeConfig::debug()` and affects runtime errors.

## Architecture

- `src/pipeline.rs` is the wiring: `parse` → `TypeTable::from_ast_decls` → `lower` (HIR + name resolution) → `check_program` → `check_borrow` → `MirGen` → `Vm`. `run_source` executes; `build_stardust` performs the same checks and goes AST→HIR→MIR→Stardust text. `freebird check` uses the same parse/resolve/type/borrow checks and emits the same diagnostics as `run`/`build`.
- `run_source` applies `#[max_stack]`/`#[max_call_depth]`/`#[max_steps]`/`#[time_limit]` from `main` to its `RuntimeConfig`. Attribute syntax/name/value validation lives in `TypeChecker::validate_attributes`.
- The `MirInst` enum lives in `src/vm/mir.rs`, not `src/mir/`; MIR generation is `src/mir/generator.rs`; the interpreter is `src/vm/mod.rs`. The VM is a dual stack (ElementId + value); read the dual-stack and `roll`/variable semantics in `readme.md` §3–4 before changing stack or variable operations.
- `typeck` and `borrowck` are wired into `run_source` and `build_stardust`. Do not bypass them when adding new pipeline entry points.
- `build --target stardust` runs and covers numeric/char values, variables, control flow (`for`/`while`/`loop`, `break`/`continue`), calls, recursion, I/O, `ret n`, scalar `as` casts, and heap-backed arrays/structs/enums/strings/Box/Vec. `file_read`/`file_write` use the bundled interpreter's `FileRead`/`FileWrite` instructions (`,` with 2/3 leading spaces), passing strings as `[chars..., len]`. `Vec`/`String`/`Box` use global heap blocks (`[len, cap, elems...]`), documented in `docs/adr/0001-logical-remote-stack.md`; `&mut` references are backed by heap cells, so writes through `*p = v` propagate back to the original variable (including when the reference is passed to another function). `--target llvm` reuses Stardust's LLVM compiler: it emits Stardust source to a temp file, runs `stardust --compile` (or `clang` for `--emit exe`), and returns the IR/binary. The Stardust binary is looked up via `--stardust-bin` → `STARDUST_BIN` → `PATH` → bundled `stardust/stardust-linux-x86_64` → sibling `../esolang_stardust/target/{release,debug}`. LLVM rejects `file_read`/`file_write` at compile time; Unicode `CharOut` is supported via `#[char_mode=unicode]` (bundled Stardust update).

## Tooling

- `freebird fmt` normalises indentation/blank lines (idempotent, comment-preserving).
- `freebird repl` (`src/repl.rs`) keeps `let`/`let mut` statements as session bindings and replays them on every input (fresh `Vm` each time), so variables stay usable across inputs; the replay re-runs initialiser expressions. History persists to `$FREEBIRD_REPL_HISTORY` → `$XDG_STATE_HOME/freebird/repl_history` → `~/.local/state/freebird/repl_history` (200 entries, multi-line inputs stored with `\u{1f}`). Line editing is intentionally not built in (std-only, offline build); docs point at `rlwrap`.
- `freebird lsp` serves stdio JSON-RPC (Content-Length framing): diagnostics via `diagnostics::collect_diagnostics`; hover/definition/references/rename/documentSymbol/completion are text-based MVP implementations in `src/lsp.rs`. Positions use LSP UTF-16 code units.
- `freebird dap` serves DAP over stdio (`src/dap.rs`): `launch` compiles via `compile_program`, breakpoints use `MirInst::Line` markers, and the VM exposes `prepare_mir`/`run_debug`/`continue_debug`/`step_debug`/`step_out_debug` plus the slice-execution API (`arm_start`/`arm_continue`/`arm_step`/`arm_step_out` + `run_debug_slice`). `next`/`stepIn` are instruction-level. `run_stdio` reads stdin on a worker thread and advances the VM in slices, so `pause` works while running (stopped reason `pause`); `variables` expands `Tuple`/`Boxed` values lazily via `variablesReference`, and `stackTrace` reports `CallFrame::current_line` per frame.
- `freebird.toml` projects: `src/manifest.rs` parses `[package] name/entry` and `[dependencies]` path entries; `pipeline::load_project` loads dependencies first with `<dep>::` prefixes, then the root entry. `run`/`check`/`build` accept `--manifest-path` or auto-detect `./freebird.toml`.
- `freebird-bench` (`src/bin/freebird-bench.rs`) records VM/Stardust/LLVM measurements in `bench/baseline.json`; `--check` compares with a tolerance and the CI `bench` job is advisory. `tests/m5_test.rs` runs fixed-seed differential fuzz, the checked-in corpus under `tests/fuzz/corpus/` (deep recursion / long loops / nested containers / enum match), and malformed-input no-panic checks; `FREEBIRD_FUZZ_SCALE` scales case count and expression depth (CI schedule job uses 10), and failures are minimized into `target/fuzz-failures/`.
- `tests/snapshot_test.rs` pins diagnostics as `code level line` in `tests/snapshots/diagnostics.txt` (update with `UPDATE_SNAPSHOTS=1 cargo test --test snapshot_test`). `scripts/check-doc-links.py`, `scripts/check-fixtures.py`, and `scripts/check-docs.py` run in CI.

## Language surface

- Builtins are registered from `src/io.rs::BUILTINS`: `print`/`print_int`, `print_char`, `print_str`, `println_str`, `read_int`, `read_char`, `read_line`, `file_read`, `file_write`, `abs`, `min`, and `max`.
- Standard library MVP: built-in generic `Option<T>` / `Result<T, E>` enums; `Option` methods `is_some`/`is_none`/`unwrap`/`unwrap_or`/`ok_or` and `Result` methods `is_ok`/`is_err`/`unwrap`/`unwrap_or`/`ok`/`err`; container methods `len`/`push`/`pop`/`is_empty`/`clear` for `Vec` and `String`. `unsafe` blocks expose a raw value stack via `push(x)`/`pop()`/`swap()`/`dup()`/`roll(n)` (backed by `MirInst::RawPush/RawPop/RawSwap/RawDup/RawRoll`; the VM keeps a `Vec<Value>`, Stardust simulates it with a heap block that doubles from 64; `roll(n)` follows readme §4.2.3); they may only be called inside an `unsafe` block, otherwise the type checker rejects them. File-level modules: `mod util;` loads `util.fb` from the same directory and registers its top-level functions as `util::f`; `use util::f;` creates an alias at name-resolution time; circular dependencies are reported structs/enums inside modules are prefixed the same way (`util::Point`) and their type references and literals are rewritten; module items are private by default and must be marked `pub` to be imported from another file. User-defined `impl Type { fn f(self) }` blocks are supported: associated functions are called as `Type::f(...)` and value-receiver methods as `x.f(...)` (names are flattened to `Type::f`); `&self` read-only methods work (the call site takes a reference and `self.field` auto-derefs); `&mut self` receivers work too: `self.field = v` writes back to the caller's variable through `MirInst::FieldStoreRef` (VM locates the target across frames, Stardust writes through the reference cell). `trait Name { fn ...; }` + `impl Trait for Type { ... }` are parsed; impl methods are flattened to `Type::name`, so calls dispatch statically through the existing method resolution (no trait-object/vtable support, no check that the type implements the trait). `format(template, args...)` (variadic; `{}` placeholders, `{{`/`}}` escapes, int/bool/char/String arguments; diagnostics T024/T025) and `int_to_str`/`str_to_int` and the `map` combinator on `Option`/`Result` work on both backends (string blocks are `[len, cap, chars...]`, so the length is at handle +0).
- Closure syntax `|params| body` / `|| body` is parsed, but executing it is not implemented: the type checker rejects closures with T018 (`UnsupportedFeature`). Capture semantics and `fn(env, args)` lowering remain future work (M6-5.3).
- Top-level `const NAME: Type = expr;` (type annotation optional) is evaluated at compile time during HIR lowering: literals, earlier consts, and unary/binary arithmetic/comparison/logic are supported. Division by zero, forward references, overflow and unsupported expressions are R008. Uses are replaced by literals, so VM/Stardust/LLVM agree. `const fn`, closures and user-defined traits remain future work.
- Tuple destructuring (`let (a, b) = ...`), struct destructuring (`let Point { x, y } = p`), enum `match` with payload bindings, `vec![...]`, arrays, `Box`, indexing, and field/index assignment work in the VM. Mutable parameters (`fn f(mut x: T)`) are not part of the syntax.
- `match` supports struct, enum (including nested payloads), tuple, literal, `or`, reference and `_` patterns, plus `..` rest patterns. Type checking rejects non-exhaustive matches, unknown variants/fields, `or` alternatives with different bindings, and refutable `let` patterns; redundant or unreachable arms produce warnings (`check` JSON includes `warning_count`).
- `if let` / `while let` are supported and lowered to `match` / `loop` in the parser. Value-position `loop` and `break value` are supported (M2-6); `break value` outside `loop` is rejected. Loop labels `'outer: loop { ... }` plus `break 'outer` / `continue 'outer` work for `loop`/`while`/`for`.
- Function pointer types `fn(A, B) -> C`, function names as values, and indirect calls are supported in the VM and Stardust (Stardust resolves calls with a generated FnId dispatch). Indirect calls support zero, one or multiple return values (`fn(A) -> (B, C)` with `let (a, b) = f()` works); the return arity of a call site is recorded by the type checker and handed to MIR as a span annotation.
- Generic declarations `struct Pair<T>`, `enum Maybe<T>`, `fn id<T>(x: T) -> T` are supported with type-argument inference from struct fields and call arguments. Built-in trait bounds are supported (`<T: Ord + Eq + Display>`, covering integers/`bool`/`char`/`String`; violations are T026). Instances are collected and registered per instantiation (`Pair<i64>` vs `Pair<String>` have independent layouts; MIR falls back to the base name). Function bodies remain shared (type-erased) because generic bodies may only use type-independent operations. Explicit turbofish type arguments (`f::<T>(...)`) are supported.
- `for pattern in iterable` iterates arrays, `Vec<T>`, `String` (yielding `char`), and `&Vec<T>`/`&String`; `continue` and `break` unwind loop-body scopes and stack slots correctly in both VM and Stardust backends. `ret n` requires an integer literal and arity matching the signature; `as` supports scalar numeric/`char`/`bool` conversions.
- M0 originally rejected `break value`, value-position `loop`, `#id`, `use`, and `extern` calls. M2-6 re-enabled value `loop` / `break value`; M2-3 implemented file modules/`use`; M3 implemented Stardust FFI. `#id` remains a compile-time error.
- Stardust FFI: `extern "stardust" { #[stardust(id = N)] fn f(...) -> ...; }` is callable only inside `unsafe`; MirGen emits `MirInst::ExternCall` and the Stardust backend emits a real `Call(id, argc)`. Missing `id` uses SipHash-2-4 of the function name mapped to `1..=999` (an ID becomes leading spaces in generated source). Duplicate/oversized IDs fail at compile time; `StardustGen` reserves extern IDs so internal FnIds never collide. The VM reports `FfiUnsupported` when execution reaches an extern call; `build --link-stardust <file>` appends external Stardust definitions for both Stardust and LLVM targets. Extern functions cannot be used as function values (rejected by the type checker). See `src/codegen/ffi.rs` and `readme.md` §10.4.
- `stardust!` supports the full Stardust shorthand set (`Push`/`Pop`/`Dup`/`Swap`/arithmetic/comparison/logic/`Store`/`Load`/`ShiftL`/`ShiftR`/`Depth`/`Pick`/`DropN`/`Reverse`/`Rotate`/`Mark`/`Jump`/`UncondJump`/`Call`/`Ret`/`NumOut`/`NumIn`/`CharOut`/`CharIn`/`DumpStack`/`DumpState`/`Breakpoint`/`Nop`). Unknown names are a parse error. Macro entry/exit emits `HideCallElement`/`RestoreCallElement`: the hidden Freebird CallElement is parked in heap slot 13 so whole-stack instructions (`ShiftL`/`Depth`/`Reverse`/...) only see user data and VM/Stardust agree. `Call(id, m[, r])` consumes `m` stack values; optional `r` (default 0) declares how many values the Freebird stack model should push (the actual Stardust return count is defined by the callee; see `docs/adr/0005-stardust-call-arity.md`). The VM reports `RawCallUnsupported`.
- Stardust backend limits: heap blocks use a free list; `VecPush`/`VecPop` are in-place and `DropVar` reclaims unescaped Vec/Box bindings, but Copy-type COW old blocks and nested container blocks are conservatively not reclaimed (see `docs/adr/0002-heap-reclamation-deferred.md`); `read_line` matches VM's UTF-8 lossy decoding and reports an I/O error on EOF (same as VM); out-of-bounds indexing triggers a division-by-zero trap because the interpreter has no custom error instruction; runtime-limit attributes only affect the VM. LLVM inherits all of these through Stardust, plus its own limits: no file I/O (compile-time error) and no Freebird runtime limits; Unicode `CharOut` is supported.

## I/O quirks

- `freebird check` emits JSON with `schema_version: 1`; every diagnostic has a stable `code` (`P`/`R`/`T`/`B`/`W` + three digits), a 1-based `span`, optional `suggestion` and `related` locations. Keep codes stable when changing diagnostics.

- `run_source` returns VM output bytes; the CLI prints them once. Assert against the returned bytes rather than process stdout.
- Stardust `read_line` decodes UTF-8 into a growable character block (starts at 16 characters, doubles as needed); invalid leading/continuation bytes and overlong/surrogate/out-of-range code points become U+FFFD byte-for-byte like `String::from_utf8_lossy`. A line ends at `\n`, and trailing `\r` characters are trimmed, so CRLF input matches VM (`read_line` trims `\n`/`\r`). EOF is an I/O error on VM and Stardust/LLVM.
- VM and Stardust both resolve `&mut` writes across call frames: `fn set(p: &mut i64) { *p = 42; }` propagates back to the caller's variable.
- `print(x); print(x)` works now: the builtin call is no longer treated as leaving an extra value on the stack.
